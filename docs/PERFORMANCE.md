# Performance

What Graphoria does per request, what it was measured doing, and what those
measurements do not cover.

Every number on this page comes from
[`packages/server/bench/results/pg.json`](../packages/server/bench/results/pg.json),
regenerated by `bun run bench`. Every claim about query shape is pinned by
[`n-plus-one.test.ts`](../packages/server/src/__test/integration/perf/n-plus-one.test.ts).

---

## Query strategy

**One statement per database per operation.** The query builder groups an
operation's root fields by database and calls the engine adapter once per group.
Two root fields against the same database are one statement; two root fields
against two databases are two.

**Nesting adds no round trip.** Child rows are correlated subqueries inside the
parent's statement, aggregated to JSON by the engine:

| Engine     | How children are aggregated    |
| ---------- | ------------------------------ |
| PostgreSQL | `json_agg`/`json_build_object` |
| MySQL      | `JSON_ARRAYAGG`                |
| SQL Server | `FOR JSON PATH`                |

So the statement count for a nested query is constant — not one per level, and
not one per parent row. The integration test asserts it directly: it counts the
statements PostgreSQL actually received via `pg_stat_statements` and gets one,
for 10 parents and for 100, at one level of nesting and at three.

**The per-parent work still exists, inside the engine's plan.** `EXPLAIN
(ANALYZE)` on the generated statement shows the child subplan running once per
parent row — 100 loops for 100 parents. That is a nested loop, and a
`LEFT JOIN LATERAL` would behave identically. What it costs depends entirely on
whether the child's foreign key is indexed:

- **MySQL/InnoDB** indexes a foreign key for you.
- **PostgreSQL and SQL Server do not.** Without an index the subplan is a
  sequential scan of the child table per parent row. With one it is an index
  scan per parent row.

If nested queries are slow on PostgreSQL or SQL Server, check for an index on
the child's foreign key column before looking anywhere else.

## Caching

`cache: { ttl }` is a **REST-operation feature**. It lives on an operation in
`graphoria.ts` and applies to that operation's REST route. There is no
GraphQL-level response cache: a GraphQL query hits the database every time.

The cache key is built from the request path, method, variables, and the
session's subject and role — so two users never share an entry, and neither do
two roles.

**Known gap:** the key carries no deployment namespace. Two Graphoria
deployments pointed at the same Redis instance, serving the same route paths,
will read each other's entries. Give each deployment its own Redis database or
instance.

## The measured numbers

PostgreSQL 18.6, 1,000 users / 10,000 projects / 100,000 tasks, 200 measured
iterations after 20 discarded as warmup, requests issued one at a time over
HTTP. Recorded 2026-09-05 on an i7-11370H (8 cores, 15 GiB, Linux 6.8, Bun
1.4.1) with the database in a container on the same host.

| Scenario             | p50 ms | p95 ms | p99 ms | What it is                                        |
| -------------------- | -----: | -----: | -----: | ------------------------------------------------- |
| `list`               |   0.92 |   1.53 |   1.93 | 100 tasks by primary key, no filter               |
| `filtered-list`      |   1.34 |   2.34 |   4.39 | 100 tasks on the indexed `(priority, completed)`  |
| `nested`             |   5.96 |   7.58 |   9.24 | 100 projects each with 10 tasks — one statement   |
| `aggregate`          |  28.09 |  45.59 |  64.50 | 5 aggregate functions over all 100k rows          |
| `filtered-aggregate` |   3.24 |   5.73 |   7.85 | the same 5 over ~5k rows reached through an index |
| `procedure`          |   0.45 |   0.77 |   0.91 | a stored routine through a `Mutation` field       |
| `cached-repeat`      |   0.37 |   0.66 |   0.99 | the `list` query over REST, served from Redis     |

Reading them:

- **The two aggregates are the same query over different row counts.** The gap
  between them is a page-count gap, not a Graphoria one. The unfiltered
  aggregate reads the whole table; the filtered one reads a slice through the
  `project_id` index.
- **`aggregate` is dominated by the engine, not by Graphoria.** Measured
  separately on 2026-09-05: hand-written SQL through the driver, Graphoria's
  generated SQL through the driver, and the full HTTP + GraphQL scenario landed
  within 1.2 ms of each other, so Graphoria's share of that scenario was about
  6%. The rest is PostgreSQL computing five aggregate functions over a
  `numeric` column, which is arbitrary-precision and roughly 65% dearer per row
  than an integer would be.
- **`cached-repeat` is the same query as `list`**, so the two are directly
  comparable: the Redis path costs about 40% of the database path here, and
  proportionally far less on a deployment where the database is a network hop
  away.

**Absolute numbers move with machine load.** Two runs of identical code on this
laptop differed by up to 1.3x on p95 during the run that produced this table,
and by roughly 2x against a run recorded the previous day on the same hardware.
Treat these as an order of magnitude and a relative ranking, not as a target.

## What these numbers are not

- **They exclude authentication.** The bench server runs with
  `auth: { enabled: false }`. No figure here includes token verification, role
  resolution, or a capability check.
- **They exclude the network.** The database is on loopback on the same host.
  A deployment with the database a hop away adds that latency to every
  scenario, and `cached-repeat` gains proportionally more than the rest.
- **They are not throughput.** Requests are issued one at a time by a single
  client co-located with the server. Nothing here measures saturation, and the
  report deliberately carries no operations-per-second column: dividing 1000 by
  the mean latency produces a number that looks like throughput and contains no
  concurrency information at all.
- **They are not a comparison with anything else.** No other product was
  benchmarked. Graphoria's README compares its feature set to Hasura CE, not its
  throughput, and nothing on this page supports a throughput comparison.
- **They cover PostgreSQL.** The suite runs against MySQL and SQL Server with
  `--engine`, but only PostgreSQL results are committed and tracked.

## The regression gate

The `Benchmark` workflow runs nightly and on manual dispatch. It benches main as
of 24 hours ago and the current head **on the same runner**, then compares the
two.

It compares two runs rather than a run against the table above deliberately.
That table is developer-machine data; a shared cloud runner is different
hardware under different load, so a threshold tuned to one is noise on the
other. A same-runner A/B cancels the hardware out and cannot go stale.

A scenario fails only when its p95 is **both** more than 1.5x the baseline
**and** more than 1 ms slower. Both bounds are needed: the ratio alone flaps on
the sub-millisecond scenarios, where run-to-run noise clears 1.5x on its own.

**Its blind spot:** a small uniform increase across every scenario clears
neither bound and passes. Demonstrated during development — a deliberate 3 ms
delay inserted into the query execution path tripped `list` (3.32x) and
`filtered-list` (3.04x) and was absorbed unnoticed by `nested` (1.42x) and
`aggregate` (1.32x), which are slow enough that 3 ms is inside their ratio.

The workflow **does not block a merge**. It is not a required check and failing
it is a signal to investigate, not a stop. Run the same comparison locally with
`bun run bench:compare`; see
[`packages/server/bench/README.md`](../packages/server/bench/README.md).
