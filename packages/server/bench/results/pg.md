## Scenarios

- `list` — 100 tasks by primary key, no filter
- `filtered-list` — 100 tasks filtered on an indexed (priority, completed) pair
- `nested` — 100 projects, each with its first 10 tasks — two levels, one statement
- `aggregate` — count/min/max/sum/avg over all 100k tasks, grouped by priority
- `filtered-aggregate` — the same five functions over the ~5k tasks of the first 499 projects
- `procedure` — stored routine through a Mutation field — the only generated write path
- `cached-repeat` — the `list` query as a REST operation with a 60s TTL, served from Redis

## Reading these numbers

Requests are issued one at a time from a client on the same host as the
database container, with authentication disabled, so the figures are
single-client service time under no contention. They are useful as a baseline to
detect regressions against, and as a relative comparison between scenarios. They
are not a saturation throughput number and they are not a cross-product
comparison.

`nested` resolves in a single statement whatever the parent count or nesting
depth — the child rows are correlated subqueries inside the parent's statement.
The per-parent work is still there, inside the engine's plan. See
`src/__test/integration/perf/n-plus-one.test.ts`.
